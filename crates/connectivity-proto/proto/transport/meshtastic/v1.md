# Meshtastic Framing 

> Status: Draft  
> Version: 1

## 1. Scope

This document defines framing and reliable delivery of an opaque Connectivity Protocol payload over Meshtastic.

The transport does not interpret the upper-layer payload. The payload MAY be a serialized `core.Message`, a serialized `SignedEnvelope`, or another object defined by the upper Connectivity Protocol layer.

The exact byte sequence supplied to this transport MUST be reproduced after reassembly.

Conceptually:

```text
upper Connectivity Protocol layer
        |
        | opaque bytes
        v
Meshtastic transport framing
        |
        | PKI unicast
        v
configured destination node
        |
        | frame validation / bounded reassembly
        v
exact original opaque bytes
        |
        v
upper Connectivity Protocol handler
```

Payload interpretation, signature verification, authorization, content-level deduplication, and application processing are outside the scope of this transport.

## 2. Normative language

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `MAY`, and `OPTIONAL` in this document are to be interpreted as normative requirements.

## 3. Design goals

The transport is designed around the following principles:

1. Preserve the upper-layer payload byte-for-byte.
2. Keep framing independent of the upper-layer payload type.
3. Use Meshtastic PKI unicast with routing acknowledgement.
4. Keep the common single-packet path as small as possible.
5. Use fragmentation only when the payload does not fit into one PKI-unicast Meshtastic packet.
6. Bound receiver-side memory and reassembly state.
7. Delegate short-timescale retries to Meshtastic firmware.
8. Treat transport framing identifiers as reassembly metadata, never as authentication or application identity.
9. Keep Meshtastic node identity separate from upper-layer Connectivity Protocol identity.
10. Use conservative packet-size limits that are valid for development with `PRIVATE_APP = 256`.

## 4. Meshtastic application port

Connectivity Protocol frames MUST use a dedicated Meshtastic application `PortNum`.

During development and controlled deployments, implementations MAY use:

```text
PortNum::PRIVATE_APP = 256
```

Production deployments SHOULD use a registered third-party Meshtastic `PortNum` in the range `64..127`.

`TELEMETRY_APP` MUST NOT be used for this transport framing.

The Meshtastic application port identifies the payload as a Connectivity Protocol transport frame. The first byte of `Data.payload` identifies the transport version and frame type.

## 5. Delivery model

This transport is defined for PKI-encrypted unicast.

Each sender MUST know the Meshtastic node identifier and public key of its configured destination before sending.

Each receiver MUST know the public key associated with an authorized sender according to deployment policy.

Recommended packet settings are:

```text
destination   = configured destination node
want_ack      = true
pki_encrypted = true
```

If PKI encryption cannot be used, the sender MUST fail the send rather than silently downgrade to channel encryption.

Meshtastic firmware is responsible for routing acknowledgement and its normal retransmission behavior.

Host-side code MUST NOT run an independent short-timeout retry loop in parallel with Meshtastic firmware retries.

After terminal Meshtastic delivery failure, higher-level policy MAY persist and retry the complete upper-layer payload later.

Gateway discovery, key provisioning, key rotation, broadcast delivery, and multi-destination fan-out are outside the scope of this framing specification.

## 6. Meshtastic PKI-unicast payload budget

Meshtastic has a 255-byte LoRa packet limit.

The on-air Meshtastic header occupies 16 bytes, leaving:

```text
255 - 16 = 239 bytes
```

for the encrypted packet payload.

Meshtastic PKI adds 12 bytes of wire overhead:

```text
8 bytes  AES-CCM authentication tag
4 bytes  extra nonce
--------------------------------
12 bytes total
```

Therefore the maximum encoded `meshtastic.Data` size for PKI unicast is:

```text
239 - 12 = 227 bytes
```

This transport assumes that `Data` contains only the fields required for application dispatch:

```protobuf
Data {
    portnum = CONNECTIVITY_PROTOCOL_PORT;
    payload = <transport frame>;
}
```

Fields with default values, including `want_response = false`, MUST remain omitted from the encoded `Data` message unless the sender has separately verified that the resulting packet still fits the Meshtastic MTU.

### 6.1 `PRIVATE_APP = 256`

For `PRIVATE_APP = 256`, protobuf encoding requires:

```text
portnum:
    field tag             1 byte
    enum varint           2 bytes

payload:
    field tag             1 byte
    length varint         2 bytes
    payload               N bytes
```

Thus:

```text
3 + 3 + N <= 227
N <= 221
```

Field measurements against production Meshtastic firmware show that the achievable unicast payload is smaller than this theoretical bound. A 2-byte conservative safety margin is reserved to account for firmware and encoding variance:

```text
N <= 221 - 2 = 219
```

The conservative Connectivity Protocol transport MTU is therefore:

```text
TRANSPORT_MTU = 219 bytes
```

### 6.2 Registered third-party PortNum

A registered PortNum in the range `64..127` requires a one-byte enum varint and can therefore provide one additional application byte.

This specification intentionally does not define a larger framing profile for registered ports.

All conforming implementations MUST use the conservative limits based on:

```text
TRANSPORT_MTU = 219 bytes
```

This keeps the framing identical between development and production deployments.

## 7. Frame types

Every Connectivity Protocol Meshtastic frame starts with a one-byte control field.

The control byte is encoded as:

```text
  7 6 5 4 3 2 1 0
 +---+-----------+
 | T |  VERSION  |
 +---+-----------+
   2       6
  bits    bits
```

Where:

```text
bits 7..6 = frame type
bits 5..0 = transport version
```

For this specification:

```text
version = 1
```

Frame types are:

| Type bits | Name | Meaning |
|---|---|---|
| `00` | `SINGLE` | Complete opaque payload follows the control byte |
| `01` | `FRAGMENT` | Fragment header and fragment body follow |
| `10` | reserved | Reserved for future protocol use |
| `11` | reserved | Reserved for future protocol use |

The version-1 control values are:

```text
0x01 = SINGLE
0x41 = FRAGMENT
```

A receiver MUST reject unsupported versions and reserved frame types.

The receiver MUST NOT infer the upper-layer payload type from transport framing.

## 8. SINGLE frame

A complete upper-layer payload that fits in one transport frame is encoded as:

```text
Offset  Size    Field
------  ------  ------------------------------
0       1       Control = 0x01
1       N       Opaque upper-layer payload
```

Where:

```text
1 <= N <= 218
```

The complete Meshtastic `Data.payload` is:

```text
+---------+----------------------------------+
|  0x01   | opaque upper-layer payload      |
+---------+----------------------------------+
  1 byte              1..218 bytes
```

A sender MUST use `SINGLE` when:

```text
len(payload) <= 218
```

The receiver MUST treat every byte after the control byte as the exact upper-layer payload.

The receiver MUST NOT decode and re-encode the payload as part of transport processing.

A zero-length `SINGLE` body is malformed and MUST be rejected.

## 9. FRAGMENT frame

A fragmented upper-layer payload is encoded as:

```text
Offset  Size    Field
------  ------  ------------------------------
0       1       Control = 0x41
1       6       Message ID
7       1       Fragment descriptor
8       N       Fragment body
```

Where:

```text
1 <= N <= 211
```

The fragment header size is:

```text
8 bytes
```

The maximum fragment body is:

```text
219 - 8 = 211 bytes
```

### 9.1 Message ID

`message_id` is the first six octets of the SHA-256 digest of the exact upper-layer payload:

```text
message_id = SHA256(raw_payload)[0:6]
```

The six octets are copied directly from the digest in digest order.

`message_id` is a byte string, not an integer. No byte-order conversion is performed.

Example:

```text
SHA256(raw_payload) =
2c f2 4d ba 5f b0 a3 0e ...

message_id =
2c f2 4d ba 5f b0
```

The 48-bit `message_id` is only a compact transport-level reassembly identifier.

It MUST NOT be treated as:

- an authentication token;
- an authorization identity;
- an application-level message identifier;
- a globally collision-free identifier;
- a replacement for a complete content hash;
- a replacement for an upper-layer signature.

Security decisions MUST NOT rely on `message_id`.

### 9.2 Fragment descriptor

The fragment descriptor packs the total fragment count and zero-based fragment index into one byte:

```text
  7 6 5 4 3 2 1 0
 +-------+-------+
 | COUNT | INDEX |
 +-------+-------+
    4       4
   bits    bits
```

The high nibble stores:

```text
fragment_count - 1
```

The low nibble stores:

```text
fragment_index
```

Decoding:

```text
fragment_count = ((descriptor >> 4) & 0x0f) + 1
fragment_index = descriptor & 0x0f
```

For fragmented payloads:

```text
2 <= fragment_count <= 16
0 <= fragment_index < fragment_count
```

Example: the second fragment of a three-fragment payload:

```text
fragment_count = 3
fragment_index = 1

descriptor =
((3 - 1) << 4) | 1
= 0x21
```

A `FRAGMENT` declaring `fragment_count = 1` is malformed and MUST be rejected.

## 10. Fragmentation algorithm

Given:

```text
raw_payload
```

the sender proceeds as follows.

If:

```text
len(raw_payload) <= 218
```

the sender MUST emit one `SINGLE` frame.

Otherwise the sender MUST:

1. Compute:

   ```text
   message_id = SHA256(raw_payload)[0:6]
   ```

2. Split `raw_payload` sequentially into chunks of 211 bytes, except that the final chunk MAY contain fewer bytes.

3. Compute:

   ```text
   fragment_count = ceil(len(raw_payload) / 211)
   ```

4. Reject the payload for this transport if:

   ```text
   fragment_count > 16
   ```

5. Emit one `FRAGMENT` frame for each chunk.

For every non-final fragment:

```text
fragment_body_length MUST equal 211
```

For the final fragment:

```text
1 <= fragment_body_length <= 211
```

The maximum upper-layer payload representable by this framing is:

```text
16 * 211 = 3376 bytes
```

A sender MUST NOT create a fragmented transport message larger than 3376 bytes.

## 11. Sending fragments

Fragments MAY be delivered by the mesh out of order.

A sender SHOULD submit fragments in ascending `fragment_index` order.

Each fragment is a separate Meshtastic packet and MUST use PKI unicast.

Each fragment SHOULD request routing acknowledgement:

```text
want_ack = true
```

The sender MUST NOT interpret successful delivery of one fragment as successful delivery of the complete upper-layer payload.

Meshtastic routing acknowledgement applies to individual Meshtastic packets, not to the reassembled Connectivity Protocol payload.

## 12. Reassembly key

Receiver reassembly state MUST NOT be keyed by `message_id` alone.

At minimum, the reassembly key MUST include:

```text
ingress_scope
mesh_sender
message_id
```

Conceptually:

```text
ReassemblyKey {
    ingress_scope,
    mesh_sender: MeshPacket.from,
    message_id:  frame.message_id,
}
```

`ingress_scope` is implementation-local metadata identifying the Meshtastic ingress context.

For a process connected to one local Meshtastic destination, the connection or gateway instance identifier is sufficient.

If one process receives traffic for multiple independently addressed local Meshtastic identities, `ingress_scope` MUST distinguish them.

`MeshPacket.channel` is not required in the reassembly key for PKI unicast.

Meshtastic sender identity is transport metadata. It MUST NOT be assumed to be identical to any upper-layer Connectivity Protocol identity unless an explicit binding exists outside this framing specification.

## 13. PKI authentication requirement

Frames defined by this specification MUST be accepted as Connectivity Protocol ingress only when the receiving Meshtastic stack reports successful PKI decryption/authentication for the packet.

A receiver MUST NOT treat:

- channel-encrypted traffic;
- plaintext traffic;
- a claimed `MeshPacket.from`;
- an unauthenticated public key claim;

as equivalent to a successfully authenticated PKI direct message.

The transport implementation MAY expose authenticated Meshtastic sender metadata to the upper layer, but upper-layer authorization policy is outside the scope of this specification.

## 14. Frame validation

The receiver MUST validate a frame before committing unbounded or attacker-controlled state.

For every packet, the receiver MUST validate:

1. The expected Connectivity Protocol Meshtastic `PortNum`.
2. Successful Meshtastic PKI authentication.
3. `Data.payload` contains at least one byte.
4. The control-byte version is supported.
5. The frame type is defined by this specification.
6. The Meshtastic destination is the expected local node identity, where available.

For `SINGLE`:

```text
1 <= body_length <= 218
```

For `FRAGMENT`:

```text
frame_length >= 9
2 <= fragment_count <= 16
fragment_index < fragment_count
1 <= body_length <= 211
```

For every non-final fragment:

```text
body_length == 211
```

For the final fragment:

```text
1 <= body_length <= 211
```

Malformed frames MUST be rejected and MUST NOT be passed to the upper Connectivity Protocol layer.

## 15. Reassembly rules

For the first accepted fragment associated with a reassembly key, the receiver creates bounded reassembly state and records:

```text
message_id
fragment_count
first_seen
last_progress
received fragment indexes
fragment bodies
```

Subsequent fragments for the same key MUST declare the same `fragment_count`.

A fragment-count mismatch is a conflict. The receiver MUST discard or poison the affected reassembly state.

Fragments MAY arrive out of order.

Reassembly completes only when every fragment index from:

```text
0 .. fragment_count - 1
```

is present.

The receiver reconstructs the upper-layer payload by concatenating fragment bodies in ascending `fragment_index` order.

After concatenation, the receiver MUST verify:

```text
SHA256(reassembled_payload)[0:6] == message_id
```

If the check fails, the reassembled payload MUST be discarded.

The digest-prefix check verifies transport reassembly consistency only. It does not establish upper-layer authenticity.

After successful reassembly, the receiver MUST pass the exact reconstructed byte sequence to the upper Connectivity Protocol handler.

## 16. Duplicate and conflicting fragments

The same:

```text
(ingress_scope, mesh_sender, message_id, fragment_index)
```

may arrive more than once.

If the repeated fragment body is byte-identical, the receiver SHOULD ignore the duplicate.

An identical duplicate MUST NOT refresh `last_progress`.

If a repeated fragment body differs, the receiver MUST treat it as a fragment conflict and MUST discard or poison the affected reassembly state.

Implementations SHOULD expose a metric for fragment conflicts.

## 17. Resource limits

A receiver MUST place finite limits on reassembly memory and state.

The wire protocol imposes:

```text
max_fragment_body     = 211 bytes
max_fragments         = 16
max_reassembled_bytes = 3376 bytes
```

An implementation MUST additionally bound at least:

```text
pending assemblies globally
pending assemblies per mesh sender
buffered bytes globally
buffered bytes per mesh sender
idle lifetime
absolute assembly lifetime
```

Recommended gateway defaults are:

```text
max_pending_global            = 128
max_pending_per_sender        = 8
max_buffered_bytes_global     = 262144
max_buffered_bytes_per_sender = 13632
idle_timeout                  = 60 seconds
absolute_timeout              = 300 seconds
```

`idle_timeout` is measured from the most recent newly accepted fragment that advanced an incomplete assembly.

Duplicate fragments MUST NOT extend `idle_timeout`.

`absolute_timeout` is measured from creation of reassembly state and MUST NOT be extended.

Expired partial assemblies MUST be discarded.

When a resource limit is reached, the receiver SHOULD reject creation of new assemblies rather than permitting unbounded growth.

## 18. Exact-byte preservation

The authoritative transport payload is the exact byte sequence supplied by the upper Connectivity Protocol layer.

For `SINGLE`:

```text
raw_payload = Data.payload[1:]
```

For `FRAGMENT`:

```text
raw_payload = concatenate(fragment_body[0..N-1])
```

Transport code MUST preserve these bytes exactly.

Transport code MUST NOT:

1. decode and re-encode an upper-layer protobuf object;
2. normalize protobuf fields;
3. reorder protobuf fields;
4. remove unknown fields;
5. alter the payload before handing it to the upper layer.

The upper layer MAY decode the payload after transport processing is complete.

## 19. Upper-layer payload type

This framing deliberately carries no `Message` vs `SignedEnvelope` discriminator.

The upper-layer payload profile MUST be agreed by protocol version, deployment configuration, application context, or another upper-layer mechanism.

Examples of valid upper-layer profiles include:

```text
serialized core.Message
serialized SignedEnvelope
future Connectivity Protocol payload
```

Adding a payload-type discriminator in the future MUST be treated as an upper-layer protocol concern unless it changes fragmentation semantics.

## 20. Ingress boundary

The Meshtastic ingress SHOULD behave as a narrow transport adapter.

Conceptually:

```text
receive Meshtastic packet
        |
        v
validate PortNum + PKI
        |
        v
parse control byte
        |
        +---- SINGLE ------+
        |                  |
        |                  v
        |             opaque bytes
        |
        +---- FRAGMENT ----+
                           |
                           v
                  bounded reassembly
                           |
                           v
                  message_id check
                           |
                           v
                     opaque bytes
                           |
                           v
             upper Connectivity Protocol
```

A transport-facing ingress record MAY contain:

```text
IngressMessage {
    payload: bytes,
    transport: Meshtastic,
    transport_metadata: {
        mesh_sender,
        mesh_destination,
        ingress_scope,
        pki_authenticated,
    },
    received_at,
}
```

The upper layer is responsible for interpreting `payload`.

## 21. ACK semantics

Meshtastic routing acknowledgement and upper-layer acceptance are distinct events.

The following states MUST be treated separately:

```text
Meshtastic ACK
    individual Meshtastic packet reached the destination node

reassembly complete
    every transport fragment was received

transport validated
    framing and message_id checks succeeded

upper-layer accepted
    payload was successfully processed by the Connectivity Protocol layer

upstream published
    accepted data was delivered to the next system component
```

A Meshtastic ACK does not prove that:

```text
the complete fragmented payload was received
the upper-layer payload was structurally valid
a SignedEnvelope signature was valid
a Message was authorized
the payload was accepted upstream
```

This transport defines no application-level receipt.

## 22. Retry behavior

Short-timescale packet retries SHOULD be delegated to Meshtastic firmware.

The host SHOULD submit each frame once with:

```text
want_ack = true
```

and observe the Meshtastic delivery result.

The host MUST NOT immediately retransmit the same frame based on its own short timeout while Meshtastic may still be performing routing-level retries.

After terminal delivery failure, higher-level application policy MAY:

- persist the complete original upper-layer payload;
- retry later;
- choose another transport;
- discard according to application policy.

A later retry MUST be generated from the same original payload bytes if exact-byte preservation is required.

## 23. Routing compatibility

Connectivity Protocol uses a custom Meshtastic application `PortNum`.

Mesh deployments carrying Connectivity Protocol traffic MUST ensure that required forwarding nodes rebroadcast the selected application port.

Nodes configured with:

```text
CORE_PORTNUMS_ONLY
```

rebroadcast only core Meshtastic ports and may drop Connectivity Protocol custom-port packets.

Deployment operators MUST verify custom-port forwarding across the intended route.

## 24. Security considerations

Meshtastic PKI provides transport confidentiality, integrity, and peer authentication for the direct-message path between the configured endpoints.

This framing does not add an independent cryptographic authentication mechanism.

The 48-bit `message_id` is not security-sensitive and MUST NOT be used for authorization.

Transport security and upper-layer security are separate concerns.

For example:

```text
Meshtastic PKI
    protects packet transport between provisioned Meshtastic peers

SignedEnvelope
    may provide portable upper-layer authenticity beyond the Meshtastic destination
```

or:

```text
Meshtastic PKI
    may be the only authenticity layer when the upper payload is an unsigned Message
```

Which upper-layer security model is used is outside the scope of this transport.

Meshtastic routing metadata remains visible to the mesh and is not made private by this framing.

## 25. Frame examples

### 25.1 SINGLE

For an opaque payload beginning with:

```text
0a 03 66 6f 6f ...
```

the Connectivity Protocol transport frame is:

```text
01 0a 03 66 6f 6f ...
^^
control = SINGLE, version = 1
```

The byte `0x0a` is the first byte of the upper-layer payload.

### 25.2 FRAGMENT

For a fragmented payload whose message ID is:

```text
2c f2 4d ba 5f b0
```

and fragment index `1` of `3`, the descriptor is:

```text
0x21
```

The frame begins:

```text
41 2c f2 4d ba 5f b0 21 ...
^^ ^-----------------^ ^^
|          |           |
|          |           +-- fragment 1 of 3
|          +-------------- message_id
+------------------------- FRAGMENT, version 1
```

## 26. Sender algorithm

A sender implementation is equivalent to:

```text
raw = exact upper-layer payload bytes

if len(raw) == 0:
    reject

if len(raw) <= 218:
    send_meshtastic_pki(
        payload = 0x01 || raw,
        destination = configured_destination,
        want_ack = true,
    )
    return

if len(raw) > 3376:
    reject for this transport

id = SHA256(raw)[0:6]
chunks = split_sequentially(raw, 211)
count = len(chunks)

for index, chunk in chunks:
    descriptor = ((count - 1) << 4) | index

    send_meshtastic_pki(
        payload =
            0x41
            || id
            || descriptor
            || chunk,
        destination = configured_destination,
        want_ack = true,
    )
```

Scheduling, queueing, duty-cycle policy, persistence, and long-term retry policy remain implementation concerns.

## 27. Receiver algorithm

A receiver implementation is equivalent to:

```text
on_meshtastic_data(packet):

    if packet.portnum != CONNECTIVITY_PROTOCOL_PORT:
        ignore

    if not packet.pki_authenticated:
        reject

    payload = packet.payload

    if len(payload) < 1:
        reject

    control = payload[0]
    version = control & 0x3f
    type    = control >> 6

    if version != 1:
        reject

    if type == SINGLE:
        raw = payload[1:]

        if len(raw) < 1 or len(raw) > 218:
            reject

        submit_upper_payload(raw, transport_metadata)
        return

    if type != FRAGMENT:
        reject

    if len(payload) < 9:
        reject

    id         = payload[1:7]
    descriptor = payload[7]
    body       = payload[8:]

    count = ((descriptor >> 4) & 0x0f) + 1
    index = descriptor & 0x0f

    if count < 2 or count > 16:
        reject

    if index >= count:
        reject

    if len(body) < 1 or len(body) > 211:
        reject

    if index < count - 1 and len(body) != 211:
        reject

    key = (
        ingress_scope,
        packet.from,
        id,
    )

    bounded_store_fragment(
        key,
        count,
        index,
        body,
    )

    if not all_fragments_present(key):
        return

    raw = concatenate_in_index_order(key)

    if len(raw) > 3376:
        discard(key)
        return

    if SHA256(raw)[0:6] != id:
        discard(key)
        return

    discard_reassembly_state(key)
    submit_upper_payload(raw, transport_metadata)
```

The receiver MUST apply configured memory, sender, idle-timeout, and absolute-timeout limits around reassembly state.

## 28. Interoperability requirements

A conforming sender MUST:

1. use the dedicated Connectivity Protocol Meshtastic `PortNum`;
2. use PKI unicast;
3. use only version-1 `SINGLE` or `FRAGMENT` frames defined here;
4. use `SINGLE` for payloads of 218 bytes or less;
5. use exactly 211 bytes for every non-final fragment body;
6. derive `message_id` as the first six raw SHA-256 digest octets;
7. preserve the exact upper-layer payload bytes;
8. address frames to the configured Meshtastic destination;
9. avoid PKI downgrade.

A conforming receiver MUST:

1. demultiplex by the dedicated Meshtastic application port;
2. require successful Meshtastic PKI authentication;
3. parse and validate the control byte;
4. reject unsupported versions and reserved frame types;
5. enforce all frame-size and fragment-count limits;
6. use sender-scoped bounded reassembly state;
7. accept out-of-order fragments;
8. detect duplicate and conflicting fragments;
9. verify the message ID after complete reassembly;
10. preserve the exact reconstructed bytes;
11. pass the payload unchanged to the upper Connectivity Protocol layer.
