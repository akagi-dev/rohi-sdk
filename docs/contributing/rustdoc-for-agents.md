# Rustdoc authoring guide (for developers and AI coding agents)

Crate-level rustdoc is the **authoritative technical documentation** of every ROHI SDK crate. A reader must understand a
crate from its docs.rs page without reverse-engineering the implementation. This guide is the canonical procedure for
writing and maintaining it. Follow it literally; where it says *must*, the PR is not done otherwise.

Where documentation lives (book vs rustdoc vs source) is defined in [Documentation style and policy](docs-style.md).
This page only covers rustdoc.

## Principles

1. **Code is the source of truth.** Verify every claim against the implementation, tests and Cargo features before
   writing it. If the code and an old doc disagree, the code wins and the doc is fixed.
2. **Explain before listing.** Purpose, concepts and usage first; the item list is generated by rustdoc.
3. **Document guarantees explicitly**: errors, ownership, concurrency, cancellation, resource bounds, persistent and
   wire compatibility, safety.
4. **Never invent.** No invented guarantees, numbers, behaviours, examples or hardware results. If you did not read it in
   code, a test, a schema or the [support matrix](../support/overview.md), do not write it. Write "not measured" or
   "not verified on hardware" instead.
5. **One authoritative place per fact.** Rustdoc owns crate contracts. The book owns user journeys and links here; do not
   copy API listings or limit tables into the book (canonical pages: see [docs-style](docs-style.md)).
6. **Examples are compiled.** A doctest that cannot rot beats a snippet that can.

## Crate-level `//!` structure

Every crate landing page uses these headings, in this order. Omit a section only when it does not apply (a docs-only or
generated crate), never reorder.

| # | Heading | Content |
|---|---------|---------|
| 1 | *(first paragraph, no heading)* | One-sentence summary shown in search results and on the crate list |
| 2 | `# Overview` | What the crate provides, when to use it, what it deliberately does not do, `no_std` / allocation / feature facts |
| 3 | `# Quick Example` | The smallest meaningful runnable example (a doctest) |
| 4 | `# Core Concepts` | The main abstractions and how they relate; tables for vocabularies |
| 5 | `# Architecture and Integration` | How it fits into firmware and the other crates; a `text` diagram or table; who owns what |
| 6 | `# API Navigation` | Table of the important modules, traits, types and macros, each an intra-doc link |
| 7 | `# Guarantees and Limitations` | Errors, resource bounds, cancellation, ABI/wire stability, feature flags, target and platform requirements, what is not verified |

Adapt the emphasis, not the skeleton:

| Crate kind | Emphasis |
|------------|----------|
| Runtime service (`rohi-time`, `rohi-net`) | state machine, config section, status issues, cancellation, resource bounds |
| Procedural macro (`*-derive`) | attribute table, generated items, compile-time errors (`compile_fail` doctest); the macro is used through the runtime crate's re-export |
| Platform adapter (`*-esp`) | chip features and targets, what is empty without a chip feature, ownership of peripherals, link to firmware |
| Generated protocol bindings (`*-proto`) | the authoritative `.proto`, public wrappers, limits, compatibility rules; do not list generated items |
| Docs-only (`rohi-sdk`) | crate map, cross-cutting contracts, links to the crate that owns each contract |

### Template

```rust,ignore
//! One-sentence summary, ends with a period.
//!
//! # Overview
//!
//! What `rohi-foo` provides and when to use it. What it does not do. Whether it
//! is `no_std`, allocation free, which Cargo features it has.
//!
//! # Quick Example
//!
//! ```
//! use rohi_foo::Foo;
//!
//! let foo = Foo::new();
//! assert!(foo.is_ready());
//! ```
//!
//! # Core Concepts
//!
//! | Concept | Meaning |
//! |---------|---------|
//! | [`Foo`] | what it is, in one line |
//!
//! # Architecture and Integration
//!
//! ```text
//! firmware task ──► Foo ──► rohi_service::Status
//! ```
//!
//! # API Navigation
//!
//! | Item | Use it to |
//! |------|-----------|
//! | [`foo`] | ... |
//! | [`Foo`] | ... |
//!
//! # Guarantees and Limitations
//!
//! - **Errors:** see [`FooError`].
//! - **Cancellation:** every `async fn` is cancel safe / not cancel safe because ...
//! - **Limits:** at most N entries, sizes are wire ABI ([Resource limits]).
//! - **Targets:** host-tested; hardware verification: not verified ([support matrix]).
//!
//! [Resource limits]: https://docs.rs/rohi-sdk/latest/rohi_sdk/memory/index.html
//! [support matrix]: https://rohi.akagi.dev/support/overview.html
```

## Item-level `///` documentation

- First line: one sentence, third person, ends with a period (`Returns ...`, `Wraps ...`).
- Then the contract: what the caller must provide, what is guaranteed, what is *not*.
- Use the standard sections where they apply, in this order: `# Errors`, `# Panics`, `# Safety`, `# Examples`.
  - `# Errors`: every error variant a caller can observe and when it occurs. Link variants with intra-doc links.
  - `# Panics`: every panic path, including `unwrap`/index/overflow in the function body. If it cannot panic, say nothing.
  - `# Safety`: required for every `unsafe fn` and `unsafe trait`; list the caller obligations, not the implementation.
- **Traits:** document the contract an *implementor* must uphold (cancellation safety, blocking, ordering, what the
  caller guarantees) on the trait and on each required method. Document provided methods separately.
- **Trait implementations:** do not repeat the trait docs; document only what is specific to the implementation.
- **Enums:** document each variant, and for error enums say who produces it and how the control plane or caller reacts.
- **Macros** (`macro_rules!`, derives): table of attributes (key, required?, meaning), the generated items, and a
  doctest; add a `compile_fail` doctest for each important rejection.
- **Feature-gated or target-gated items:** state the gate in prose (`Available with the esp32c3 or esp32c6 feature`).
  Do not link with intra-doc links to items that do not exist in every documented configuration (see
  [Validation](#validation)); use plain code font instead.
- **Constants and limits:** state the value only if it is the single source of truth (the constant itself); otherwise link
  to [Resource limits](https://docs.rs/rohi-sdk/latest/rohi_sdk/memory/index.html).
- **Persistent and wire formats:** state what is ABI (ids, field numbers, section versions) and link
  [Persistent ABI](https://docs.rs/rohi-config).
- **Public vs internal:** `pub(crate)` and private items need comments only when they hold an invariant. Do not
  document internals on public pages; put them in plain `//` comments next to the code.

### Good and bad

Bad: restates the signature, invents a guarantee, no error contract.

```rust,ignore
/// Creates a new storage.
///
/// This is very fast and never fails on all supported flash chips.
pub fn new(flash: F, region: FlashRegion) -> Result<Self, EspStorageError>
```

Good (from `rohi-config-esp`): states the precondition, every error and the compile-time constraint.

```rust,ignore
/// Wraps `flash`, restricted to `region`.
///
/// The region must be non-empty, erase-sector aligned and inside the
/// flash capacity.
///
/// # Errors
///
/// [`EspStorageError::InvalidRegion`] if the region is empty, its offset
/// or length is not a multiple of `F::ERASE_SIZE`, its end exceeds the
/// flash capacity, or its end does not fit in `u32`.
pub fn new(flash: F, region: FlashRegion) -> Result<Self, EspStorageError>
```

Bad (hardware claim without evidence): "Tested on ESP32-C6, takes about 20 ms to erase."
Good: "Erase duration is not measured; `esp-storage` runs flash routines in a critical section." State only what the
[support matrix](../support/overview.md) and the validation pages record.

A well-documented derive (from `rohi-service-derive`): the crate page has Overview, a runnable Quick Example, a table
of generated items, the naming rule, and says that the id is wire ABI. Use it as the model for macros:

```rust,ignore
/// ```
/// use rohi_service::Service;
///
/// #[derive(Service)]
/// pub struct WifiService;
///
/// assert_eq!(WifiService::NAME, "wifi");
/// assert_eq!(WifiService::ID, rohi_service::service_id("wifi"));
/// ```
```

## Technical accuracy

Before writing a sentence about behaviour:

1. Read the implementation of the function or type, not only its signature.
2. Read the tests: they show intended edge cases (and sometimes the documented behaviour is wrong).
3. Read `Cargo.toml` for features and dependencies; read `build.rs` and `.proto` files for generated code.
4. Search for callers (`firmwares/altruist-urban`, `examples/`) to see the real integration pattern.

Then classify each statement:

| Kind | Where it belongs |
|------|------------------|
| Public guarantee (callers may rely on it, changing it is breaking) | item docs, stated as contract |
| Implementation detail (may change) | plain code comments, or label it "currently" |
| Wire/persistent ABI | item docs plus a link to [Persistent ABI](https://docs.rs/rohi-config) |
| Unmeasured or unverified | say so explicitly |

Always document, where relevant:

- **Ownership:** who owns the peripheral, buffer or task; what `&mut self` / `&self` implies; what must be `'static`.
- **Async and cancellation:** whether dropping a future mid-way is safe and what state remains. The canonical rules are
  in [Async and cancellation](https://docs.rs/rohi-sdk/latest/rohi_sdk/cancellation/index.html); link them, do not restate them.
- **Resource bounds:** capacities of `heapless` collections, buffer sizes, queue depths, timeouts and what happens
  at the limit (error, drop, block).
- **Compatibility:** section ids and versions, field numbers, hash algorithms (these are ABI).
- **Platform:** which chip features and targets compile, what is an empty crate without a feature.
- **Experimental or planned:** use the words "implemented", "planned", "not verified"; never describe a plan as a feature.
- **Hardware results:** never write one. The only sources are `device-matrix.toml` and the validation pages.
  Distinguish **host-tested** (unit tests/doctests), **target-built** (CI builds the ESP target) and
  **hardware-verified** (recorded evidence).

## Examples and links

- **Prefer doctests that run on the host.** Portable crates must have at least one in the landing page.
- Use hidden lines (`# use ...;`) only for imports and boilerplate that does not hide a requirement the reader needs.
- Choose the code-block attribute deliberately:

| Attribute | Use when |
|-----------|----------|
| *(none)* | the default; the example compiles and runs on the host |
| `no_run` | compiles on the host but needs hardware, a network or never terminates |
| `compile_fail` | demonstrates a deliberate rejection (macro error, borrow rule); keep it specific |
| `should_panic` | demonstrates a documented panic |
| `text` | diagrams, wire layouts, shell output, chip-only snippets that cannot compile on the host |
| `ignore` | almost never; allowed only with a comment saying why it cannot compile anywhere. **Never use `ignore` to bypass a broken example: fix it.** |

- Chip-only (`*-esp`) examples cannot be doctested on the host. Show a short `text` excerpt or link the maintained
  source (`firmwares/altruist-urban`, `examples/src/bin`) instead of copying large blocks of implementation.
- **Intra-doc links** for every Rust item: ``[`Type`]``, ``[`module::function`]``, ``[`rohi_config::Value`]``. Do not
  hand-write docs.rs or `../rohi_x/index.html` URLs for dependencies. A relative `../rohi_x/index.html` is allowed only
  when the target is not a dependency (for example a lower crate pointing at the firmware-facing crate, or the
  docs-only `rohi-sdk`).
- Items that exist only with a chip feature must not be intra-doc linked from pages that are also built without it
  (host `cargo doc` would fail with `-D warnings`). Use code font: `` `EspWifi` ``.
- Links to the book use `https://rohi.akagi.dev/...`; links to sources use repository paths in code font.
- Tables for vocabularies, limits and error maps; `text` diagrams for structure and data flow.
- Name the project "Robonomics Open Hardware Interface (ROHI)".

## Agent workflow

Follow these steps for every crate you touch:

1. **Inspect** the public API (`cargo doc --no-deps -p <crate> --open` or read `lib.rs` exports), the implementation,
   tests, `Cargo.toml` features and callers.
2. **Identify** missing, wrong, obsolete and invented documentation. Write the list down.
3. **Update the crate landing page**: fill the seven sections from the template, with concepts and navigation.
4. **Document the affected public items**: contracts, `# Errors`, `# Panics`, `# Safety`.
5. **Add or repair examples**: a Quick Example plus a focused doctest per important trait, macro and integration
   pattern. Replace every `ignore`.
6. **Run the checks** from [Validation](#validation).
7. **Inspect the rendered docs** (`cargo doc --no-deps -p <crate> --open`): headings, tables, links, diagrams.
8. **Report** in the PR what was verified (commands, tests) and what could not be validated (hardware, chip-only
   doctests, external URLs).

## Validation

Run through `nix develop --command bash -c '<command>'` when `cargo` is not on `PATH`.

```bash
# portable crates: broken links and rustdoc warnings are errors
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps

# doctests and unit tests (host default-members)
cargo test --doc
cargo test

# lints
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check

# one crate while you work
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -p rohi-time
cargo test --doc -p rohi-time

# ESP crates: one chip per invocation, never --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -p rohi-hal-esp -p rohi-config-esp -p rohi-net-esp \
  --no-default-features --features esp32c3 --target riscv32imc-unknown-none-elf
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -p rohi-hal-esp -p rohi-config-esp -p rohi-net-esp \
  --no-default-features --features esp32c6 --target riscv32imac-unknown-none-elf

# the book (mdBook): build and snippets
mdbook build docs && mdbook test docs
```

CI (`.github/workflows/ci.yml`, job `docs`) runs the same rustdoc commands with `-D warnings` for the portable crates
and for the ESP crates on both chips; the `host` job runs `cargo test` (which includes doctests). A failing doc build
blocks the PR. Targets and features: [Targets and features](https://docs.rs/rohi-sdk/latest/rohi_sdk/portability/index.html#targets-and-features).

Doctests of derive macros live in the macro crate and use the runtime crate (`rohi-service`, `rohi-config`) as a
dev-dependency.

## Review checklist

Apply to every PR that changes public API or documentation:

- [ ] Every claim was verified against code, tests, schema or the support matrix; nothing invented.
- [ ] The crate page follows the seven-section template (or states why a section is omitted).
- [ ] New or changed public items have a contract, `# Errors`, `# Panics`, `# Safety` where applicable.
- [ ] Ownership, cancellation, resource bounds and ABI/wire compatibility are stated where relevant.
- [ ] Examples are doctests; no `ignore` without a reason; hardware-only code is `text` or a link to maintained sources.
- [ ] Intra-doc links are used; no chip-gated item is linked from a page built without the chip feature.
- [ ] Verification wording separates host-tested, target-built and hardware-verified; no unrecorded hardware result.
- [ ] `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` and the ESP doc builds pass; `cargo test --doc` passes.
- [ ] The book page for the concept only links to the rustdoc (no copied API listings or limit tables).
- [ ] The [support matrix](../support/overview.md) is updated when a board, driver or hardware result changed.
